## Общий клиент, маршрутизация и совместимость

`backend.app.llm.client` — общее место для `ChatCompletionsConfig`,
`ChatCompletionsClient` и существующих безопасных ошибок `LLM*`. Старые импорты
из `agent.config` и `agent.api_client` остаются совместимыми через re-export,
а не через вторую реализацию транспорта. Лимиты одного запроса, проверка
обрезанного ответа, неизвестный usage и классификация timeout сохраняются.

`ModelRouter(base_config, routes, approved_model_ids=...)` хранит явное
соответствие задач подтверждённым model ID. `config_for(task)` возвращает
конфигурацию, `client_for(task, transport=...)` создаёт отдельный HTTP-клиент.
При `routes=None` используется один явно разрешённый базовый model ID для всех
корректных имён задач. При переданной таблице маршрутов неизвестная задача
отклоняется; fallback к другой модели не выполняется.
В коде известен ID `deepseek/deepseek-v4.1-flash`, предоставленный для ранее
выполненного пользователем live-теста. Другие ID не выводятся из названий
семейств Qwen/GLM/DeepSeek: требуются подтверждение и явный allowlist. Router
требует `approved_model_ids` явно; константа не является allowlist по умолчанию.
Router не добавляет скрытых повторов, автоматического выбора модели или fallback.

Импорт общего пакета не должен запускать приложение, читать `.env`, создавать
БД или отправлять запрос. Настройки и авторизация передаются явно. `from_env`
остаётся отдельной вызываемой операцией, а не побочным эффектом импорта.

## Командный бюджет: рабочая граница и обязательные зависимости

`budget_guard.py` предоставляет `TokenUsage`, `RateCard`, `BudgetWindow`,
`BudgetReservation`, `BudgetGuard` и `BudgetedChatCompletionsClient`.
Денежные значения вычисляются через `Decimal` по явно подтверждённым тарифам
в рублях за миллион токенов. `RateCard.reference` указывает источник тарифа;
встроенных выдуманных цен и пересчёта долларов по предполагаемому курсу нет.
Reasoning-токены нельзя повторно прибавлять к общему usage или автоматически
считать бесплатными: их тарификация определяется явно переданным rate card.
Без отдельного reasoning-тарифа ко всем completion-токенам применяется выходной
тариф. С отдельным тарифом цена reasoning-подмножества заменяется, а не добавляется
повторно; неизвестный размер этого подмножества не позволяет закрыть резерв.

Перед HTTP-вызовом `BudgetGuard.reserve(model, max_input_tokens=...,
max_completion_tokens=...)` резервирует верхнюю границу стоимости. После
вызова `settle(reservation, usage)` заменяет резерв известной фактической
стоимостью. Это относится и к ошибочному/обрезанному ответу, если провайдер
успел вернуть достоверный usage. Неизвестный usage и отмена не доказывают
отсутствие списания: резерв остаётся до сверки, а не возвращается в бюджет.

Обязательный `BudgetStore` внедряется извне. Его `reserve` должен атомарно
проверять сумму уже потраченного и всех резервов команды во всех процессах
против лимита; `settle` должен быть идемпотентным. Модуль не подменяет эту
зависимость локальным словарём. Backend1 должен предоставить устойчивый общий
Redis/SQL store с проверками гонок, сбоев и повторной доставки. Тестовый fake
store не является реализацией для production.

Вызовы store ограничены `store_timeout_seconds` (по умолчанию 5 секунд).
Тайм-аут не освобождает уже записанный резерв. При отмене HTTP клиент сразу
распространяет отмену и оставляет существующий резерв для внешней сверки,
без ожидания второго обращения к store. Бюджетный клиент сериализует свои
вызовы, чтобы mutable usage одного запроса не закрывал резерв другого;
для независимой telemetry по-прежнему создавайте отдельный клиент на job.

Окно бюджета задаёт `window_provider`: `BudgetWindow` содержит ID и точные
начала/конец с часовым поясом. Нельзя самостоятельно предполагать часовой пояс
организаторов, момент сброса или освобождать неизвестные резервы по TTL. Дефолт
`daily_limit_rub=Decimal("500")` не назначает правильное окно суток. Переход
между окнами и сверку незавершённых резервов необходимо согласовать отдельно.

`BudgetedChatCompletionsClient` требует `budget_guard` и доверенную функцию
`input_token_bound`. Это должна быть верхняя граница токенов полного запроса
для конкретного провайдера, включая служебные сообщения, а не произвольное
отношение символов к токенам. Неверная граница или превышение её провайдером
может привести к перерасходу: последующий учёт не отменяет уже сделанное
списание. Превышение фиксируется и блокирует следующие резервы.

Подключение к существующему агенту строится явно:

```python
from backend.app.agent.runtime import RuntimeAgentEngine
from backend.app.llm.budget_guard import BudgetGuard, BudgetedChatCompletionsClient

# Все зависимости ниже передаются интегратором; пример не читает настройки.
guard = BudgetGuard(
    store=shared_atomic_store,
    team_id=authorized_team_id,
    window_provider=confirmed_budget_window,
    rate_cards=confirmed_rub_rates,
)
runtime = RuntimeAgentEngine(
    client_factory=lambda: BudgetedChatCompletionsClient(
        router.config_for("insight"),
        budget_guard=guard,
        input_token_bound=confirmed_request_token_bound,
    ),
    source_factory=authorized_analytics_source_factory,
    approved_model_ids=confirmed_model_ids,
)
```

`router.client_for` возвращает обычный клиент без денежного guard; если нужен
общий лимит, применяйте конфигурацию router к бюджетному клиенту, как выше.
Все пути запросов, включая Q&A, repair, smoke/live-harness и другие сервисы,
должны проходить через общий guard. Per-run лимиты агента остаются отдельной
защитой и не заменяют командный бюджет.

**Полная защита общего лимита ещё не подключена:** производственный общий store,
подтверждённые тарифы, окно сброса и маршрутизация всех вызовов не предоставлены.
Без обязательных зависимостей guard должен запрещать запрос, а не считать
остаток бюджета достаточным. Само наличие этого модуля не доказывает соблюдение
дневного лимита всей командой.

## Кэш проверенных результатов

`make_verified_cache_key` требует tenant, user и company scope, конфигурацию
модели, версию промпта, сам промпт, полный бизнес-контекст и версию источников.
Данные входят в digest; ключ не содержит открытый текст промпта. Важно изменять
`sources_version` при обновлении корпуса: один прежний URL не описывает версию
содержимого и provenance. При смене модели/настроек/контекста совпадение ключа
не предполагается.

`VerifiedJsonCache(max_entries=128, ttl_seconds=300)` — ограниченный локальный
opt-in кэш. `put_verified(key, payload)` принимает только полный JSON companion
с совпадающей компанией, успешной verification без issues и структурами
`insight`/`analysis`. `get(key)` возвращает независимую JSON-копию без `report`:
usage старого LLM-вызова нельзя учитывать повторно при попадании в кэш.
Это граница JSON, а не автоматическая подмена `generate_analysis`; вызывающий
код отдельно формирует отчёт cache hit и нужную типизированную проекцию.

Маркер `verification.passed` в произвольном JSON не является криптографическим
доказательством. Записывать следует только результат собственного доверенного
verifier. Авторизация, свежесть источников и инвалидация при смене прав остаются
обязанностью вызывающего приложения. Кэш не объявляется межпроцессным или
долговременным хранилищем и автоматически в агентный цикл не включается.

## Публичные контракты: что передать Backend1

Существующий `MLInsightResult`, `EvidenceItem`, `InsightResponse` и интерфейс
`generate_insight` сохраняются. Общий клиент не регистрируется в worker и не
меняет действующие HTTP-ответы автоматически.

Обнаруженные расхождения в `origin/Backend` требуют отдельной согласованной
работы:

1. `schemas/agent.py` определяет `AgentTraceStepSchema`, `JobCreateResponse` и
   `JobStatusResponse`. Они используются старым деревом `api/insights.py` и
   `api/streams.py`. В то же время `main.py` подключает `api/v1/router.py`,
   где используется `schemas/job.py`. Требуется выбрать обслуживаемое дерево
   маршрутов и свести дубли без незаметного изменения URL и форматов.
2. `schemas/stream.py::StreamEventSchema` требует `timestamp` и не содержит
   `status`. Реальные payload `status/completed/failed` передают `status`, но
   не передают `timestamp`. Обработчики сейчас не валидируют события этой
   схемой. Нельзя просто включить её в SSE: сначала согласовать поля по типам
   событий, совместимость с frontend и тесты истории/живого потока.
3. Старый `EvidenceItem` не содержит `source_id`, точную цитату, document ID,
   страницу, hash, provenance и ссылки гипотез на факты. Внутренний
   `AgentAnalysisResult` содержит более подробные основания; сохранение одного
   `MLInsightResult` их теряет. Нужен согласованный companion DTO и persistence,
   если эти основания должны быть доступны после завершения задания.
4. Новые форматы управленческих действий и grounded Q&A ещё не являются
   опубликованными HTTP-контрактами. Нельзя принимать произвольный клиентский
   `AgentAnalysisResult` как доверенный проверенный анализ. Backend должен
   получать его из авторизованного хранилища и проверять принадлежность компании.

Будущие публичные DTO должны оставаться независимыми от `agent.runtime` и
внутренних control messages. Импорт внутренних моделей агента из `schemas/`
создаёт обратную зависимость и риск цикла через `MLInsightResult → EvidenceItem`.
Преобразование внутреннего результата в согласованный DTO следует выполнять
на границе интеграции, сохраняя provenance и различие фактов и гипотез.

## Реальные источники: что передать Backend2 / Data

`BackendAnalyticsSource` умеет ранжировать явно переданные записи и сохранять
проверенные метаданные. Это адаптер, а не готовый ingestion/RAG банковских PDF.
Для реального корпуса требуются разрешённые документы, извлечение текста с
достоверными страницами, document ID/hash, даты публикаций, правила обновления
и авторизации. Флаг банковского источника и URL не подтверждают provenance.

Платёжные связи должны оставаться выборкой переводов; они не доказывают отношения
поставщик–покупатель, выручку или полноту оборотов. Источники, кэш и результаты
необходимо изолировать по компании и разрешённому контексту доступа.

## Проверки и оставшиеся интеграции

В этой задаче используются только автономные тесты, scripted clients и HTTP
mock transports. Реальные LLM-запросы, чтение ключей и обращения к настоящей БД
не выполняются. Пользователь ранее самостоятельно провёл live-тест; результаты
того запуска не доказывают готовность нового общего контура.

Для полностью подключённого MVP ещё нужны регистрация движка в lifecycle/worker,
явно подтверждённые настройки моделей и авторизации, реальный retrieval,
сохранение структурированных оснований и usage, согласованные HTTP/SSE DTO,
подключение frontend и сквозная проверка приложения. Простое появление общего
каталога или успешный автономный тест не завершает эти работы.
