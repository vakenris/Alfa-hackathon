# Интеграция агента с backend

Этот документ описывает реализованные интерфейсы внутри `backend/app/agent/` и
работы, которые должен выполнить состав приложения за пределами модуля. Наличие
автономных тестов не означает, что worker, публичные API или настоящие источники
уже подключены. Нового backend или отдельного сервиса здесь нет.

## Основной путь анализа

`AgentInsightEngine` по умолчанию использует `AgentConfig(analysis_mode="grounded")`.
Нужно явно передать клиент с интерфейсом `async generate(prompt) -> str`.
Вызов анализа без явно переданного клиента завершается ошибкой конфигурации.

Входы остаются совместимыми с существующим backend:

```python
await engine.generate_insight(company, event, counterparties, tracer)
await engine.generate_analysis(company, event, counterparties, tracer)
```

Первый метод возвращает существующий `MLInsightResult`. Второй возвращает
`AgentAnalysisResult`: `company_id`, `event_id`, `insight`, структурированный
`analysis`, `business_context`, `sources`, `verification` и безопасный `report`.
Это companion DTO для сохранения оснований и отчёта; возвращаемый `insight`
содержит совместимую проекцию для действующего backend.

Модель выдаёт `DraftInsight` с цитируемыми фактами, условными гипотезами влияния,
признаками компании, допущениями, потребностями в данных и действиями. Свободный
старый `MLInsightResult` не принимается в grounded-пути. Проверка выполняется до
детерминированного формирования шести текстовых блоков. При недостаточном
контексте допустим результат `applicability="insufficient"` без выдуманных
последствий и действий, с указанием недостающих данных.

Проверки ограничены исполняемыми правилами. Цитата из видимого источника,
существующая ссылка на факт и условная формулировка не доказывают истинность
экономической причинной связи. Результат требует экспертной оценки.

Цитирование должно сохранять завершённое предложение, включая отрицание и
условия; выбор удобного фрагмента внутри предложения отклоняется. Структурированный
числовой факт требует привязанных к цитате сущности, метрики, периода и единицы.
Несколько числовых фактов без нормализованного scope отклоняются, чтобы удаление
метаданных не обходило проверку противоречий. Одиночная числовая цитата с
неустановленным scope получает предупреждение `NUMERIC_SCOPE_UNRESOLVED` и не
становится подтверждённым расчётом эффекта для компании.

## Runtime и зависимости

`RuntimeAgentEngine` создаёт отдельные клиент и источник для каждого запуска:

```python
from backend.app.agent.backend_source import BackendAnalyticsSource
from backend.app.agent.runtime import RuntimeAgentEngine

runtime_engine = RuntimeAgentEngine(
    client_factory=make_configured_llm_client,
    source_factory=lambda: BackendAnalyticsSource.from_repository_factory(
        session_factory,
        provenance_resolver=resolve_trusted_provenance,
    ),
    approved_model_ids=frozenset(confirmed_gateway_model_ids),
)
```

Все имена зависимостей в этом примере передаёт composition root приложения.
`confirmed_gateway_model_ids` — подтверждённые организаторами API aliases,
не придуманный список. Production HTTP-клиент требует точного совпадения модели
с этим явно переданным списком. Пример не является командой запуска API.
Фабрика клиента должна возвращать новый настроенный экземпляр для задания.
Фабрика источника также должна возвращать новый объект. Runtime не загружает
`.env`, не выбирает endpoint, модель или авторизацию и не открывает соединения
при импорте. Реальный транспорт `ChatCompletionsClient` и его типизированная
конфигурация переиспользуются из `backend.app.llm.client`; прежние импорты agent
сохранены. Подключение рабочего API выполняется
через явно переданную конфигурацию.

Для `RuntimeAgentEngine` обе фабрики обязательны. По умолчанию
`FakeLLMClient` и `MockAnalyticsSource` отклоняются. Автономные тесты могут явно
задать `allow_test_dependencies=True`. Эта проверка обнаруживает известные
классы заглушек; подлинность произвольной пользовательской фабрики должен
обеспечить состав приложения.

Отчёты и источники принадлежат одному запуску и возвращаются с его результатом.
У общего engine нет поля «последний отчёт». При изменении модели управления
HTTP-клиентами Backend1 определяет их создание, закрытие и поведение при отмене.

`CompatibilityInsightEngine` предназначен для прежнего формата JSON и старых
smoke-проверок. Его результаты не подтверждают прохождение grounded-проверок.
Рабочий runtime требует grounded-конфигурацию. Старые smoke-команды и их
совместимые фикстуры не следует использовать как оценку качества анализа.

## Источник банковских материалов

`BackendAnalyticsSource(document_loader, candidate_limit=50)` реализует
`AnalyticsSourceProtocol`. Loader имеет интерфейс
`async document_loader(limit) -> list[AnalyticsDocument]` и передаётся явно.
Адаптер исследует ограниченную выборку, использует тему запроса и заголовок
события, учитывает русские формы слов и несколько словарных тем. Пустой или
неизвестный запрос не означает выдачу первых случайных публикаций.

`from_repository_factory(session_factory, provenance_resolver=None)` использует
существующий `NewsRepository.list_bank_analytics(limit<=50)`. Импорт репозитория
и открытие сессии происходят только при явном поиске. Сессия закрывается после
получения материалов. При импорте самого адаптера backend DB/core не загружаются.

Охват источника: `coverage="newest_bounded_bank_articles"`, до
`candidate_limit<=50` последних материалов. Это лексический поиск по кандидатам,
не загрузка PDF и не RAG. Более ранняя релевантная публикация может не попасть
в кандидаты. Дата разрешает равные оценки; старые документы не отбрасываются
автоматически, поскольку могут использоваться как исторический контекст.

Успешный поиск без совпадений возвращает `[]`. Ошибка loader или репозитория
распространяется как ошибка и не подменяется пустой выдачей. Инструмент агента
передаёт ограниченность данных в контекст; это не подтверждение отсутствия
публикаций во всём корпусе.

Репозиторный материал по умолчанию имеет `provenance_status="unverified"` и
`source_url=None`. Метка `is_bank_analytics=True`, название источника и ссылка
в тексте не делают его официальной публикацией. Адаптер не строит URL из
названия и не загружает произвольные ссылки.

Доверенный `provenance_resolver(row)` может синхронно или асинхронно вернуть
поля `source_url`, `provenance_status`, `source_document_id`, `source_page`,
`source_hash`. Он должен опираться на проверенный реестр предоставленного
корпуса. Статус `verified` нельзя присваивать автоматически всем строкам.
Resolver не должен подменять статью или загружать ссылки из её текста.

Для официальной позиции банка grounded-проверка требует банковский материал,
статус `verified`, непустой `source_document_id` и цитату из видимого `content`.
Результат сохраняет источник и дату. Материал позже даты анализируемого события
не принимается как основание; исторические материалы получают предупреждение.
URL, страница и hash передаются при наличии подтверждённых метаданных. Отсутствие
URL не является поводом его придумывать. Если подтверждённой позиции нет,
`bank_view` сообщает об её отсутствии. Банковский документ не обязателен для
каждого полезного инсайта.

## Управленческие действия и вопросы

`ManagementActionEngine(core)` получает явно настроенный grounded
`AgentInsightEngine`. Его интерфейсы:

```python
await actions.analyze_action(request, analysis=analysis, company=company, tracer=tracer)
await actions.answer_question(question, analysis=analysis, company=company, tracer=tracer)
```

`ManagementActionRequest` содержит `company_id`, `kind` и параметры выбранного
действия. Поддерживаются `rate_scenario`, `investment_budget`, `review_plan`,
`question`. Для сценария ставки обязателен `rate_direction` со значением `up`,
`down` или `unchanged`; направление является условием пользователя, не прогнозом.
Для вопроса обязателен непустой `question`. Модуль формирует предложения и не
изменяет действующий план, не исполняет операции и не создаёт поручения во
внешних системах.

Возвращается `ManagementActionResult` с `company_id`, `event_id`, `action_kind`,
`status`, `analysis_kind`, пояснением, допущениями, гипотезами, предложениями,
недостающими данными, вопросами, расчётами при наличии исходных параметров,
ссылками на факты, признаками компании, ограничениями, дисклеймером и `RunReport`.
Для budget/review поле `provided_financial_inputs` сохраняет предоставленные
финансовые значения и их объявленное происхождение.
Статусы: `complete`, `needs_data`, `insufficient_evidence`. Значение `complete`
обозначает подготовленный ответ, а не принятое или исполненное решение.
Каждое предложение требует проверки человеком.

Для численной чувствительности передаётся `LoanSensitivityInput`: `company_id`,
`principal`, `currency`, `rate_type`, `delta_contract_rate`, `days`,
`day_count_basis`, `reset_within_horizon`, `provenance`. Суммы и ставки представлены
через `Decimal`; валюта задаётся явно, база дней — `360` или `365`.
`delta_contract_rate` — явно предоставленная годовая договорная разница ставки
в долях: `0.01` означает один процентный пункт. Её нельзя подставлять из изменения
ключевой ставки. Ненулевая разница требует явно указанного пересмотра условий
в заданном горизонте. Флаг кредита, фиксированная ставка и новость не заменяют
договорных параметров.

Формула ограничена простой чувствительностью:
`principal * delta_contract_rate * days / day_count_basis`. Это не финансовый
прогноз; погашения, комиссии, капитализация и прочие договорные особенности
не моделируются. При отсутствии входов сохраняется качественный сценарий и
указываются пробелы. Несовпадение компании у финансовых входов отклоняется.

Для `investment_budget` и `review_plan` нужны `FinancialInputs` с `company_id`,
`available_cash`, `planned_capex`, `currency`, `provenance` и непустой
`current_plan: list[PlanItem]`. Пункт плана содержит `id`, `title`, `provenance`;
дополнительно можно передать `related_channels`. Идентификаторы уникальны.
Предложения ссылаются только на пункты с заданной либо лексически предполагаемой
связью с применимым каналом; эта связь требует проверки человеком.
Параметры должны быть объявлены фактическими через
`InputProvenance(data_mode="actual", reference=...)`; поддерживается также
отдельная маркировка `hypothetical`. Объявление пользователя не является
независимой документальной проверкой. Без фактических входов и действующего
плана возвращаются потребности в данных вместо выдуманного пересмотра бюджета.

Вопрос использует только основания переданного анализа. Модель может выбирать
существующие идентификаторы фактов, гипотез и признаков, а также предусмотренные
типы пробелов; итоговая формулировка собирается программно. Произвольный новый
финансовый ответ модели не публикуется. Неверный выбор допускает не более одного
исправления в пределах лимита вызовов. Неизвестный вопрос и отсутствие оснований
выражаются через потребность в уточнении.

Ставочный сценарий, budget/review и неизвестный вопрос обрабатываются программно
без LLM-вызовов. Релевантный вопрос использует один вызов для выбора ссылок и
при необходимости один ограниченный вызов исправления. Отсутствующие вызовы
не являются измерением стоимости API; usage и цена не выдумываются.

Передавайте `analysis` только из доверенного хранилища авторизованной компании.
Модуль проверяет совпадение `company_id`, известных признаков текущего профиля,
ссылок и проекции evidence. Companion DTO не содержит полных исходных документов:
по нему нельзя заново проверить каждую цитату или удостоверить целиком подделанный
bundle. JSON, произвольно присланный клиентом, нельзя считать проверенным анализом.
Новые HTTP endpoints, persistence и публичный формат действий согласуют Backend1
и ML; этот модуль не регистрирует их самостоятельно.

## Область компании и семантика данных

Компания, событие и выборка платежей передаются в каждый запуск явно.
Авторизацию компании, принадлежность сохранённого инсайта пользователю и
tenant isolation должен проверять вызывающий API до передачи данных агенту.
Идентификатор компании в JSON сам по себе не является авторизацией.

В companion-результате сохраняются `company_id` и `event_id`; их необходимо
проверять при последующих управленческих действиях и вопросах. Источники и
отчёты другой компании нельзя добавлять в новый контекст. Runtime не хранит
общую историю сообщений для всех компаний.

Семантика исходного кейса учитывается с ограничениями: `NEGATIVEMARK` относится
к ключевому собственнику; `1000` в выручке считается заглушкой; известная выручка
интерпретируется как рубли за 2025 год. Другой источник требует явного
согласования года и валюты. Отсутствующий или отрицательный продуктовый флаг
не раскрывает остатки и договорные условия. Страны ФТС не определяют валюту,
направление или объём торговли. Сегмент группы не вычисляется из одного профиля.

Платежи остаются выборкой финансовых операций. Направления нормализуются как
`incoming`, `outgoing`, `self_transfer`, `unknown`; факт перевода не устанавливает
отношение «поставщик–покупатель». Self transfers выделяются отдельно. FAQ задаёт
начало периода с 1 января без предоставленного года и окончания; агент не
добавляет эти даты самостоятельно. Доля self transfers по всему набору не
переносится на конкретную компанию.

## Отчёт запуска и бюджет

`result.report` содержит ограниченные технические поля: вызовы и их длительности,
известный usage, причины остановки, тайм-ауты, отмены, безопасные коды ошибок,
сводки проверки и источников. Ошибки `AgentError` могут содержать `run_report`
для уже начатого запуска. Промпты, авторизация и содержимое инсайта не должны
попадать в технические журналы.

Лимит вызовов расходуется до запуска следующего запроса. Пересборка ответа и
исправление также укладываются в общий лимит; число исправлений ограничено.
Неизвестный usage остаётся `null`, `known_subtotal` содержит только известную
часть. Количество символов не превращается в оценку токенов или рублей.
Отмена клиента не подтверждает отсутствие списания у провайдера.

Общий `llm/budget_guard.py` предоставляет резервирование, settlement и бюджетный
подкласс существующего HTTP-клиента. Backend1 совместно с ML внедряет общий
атомарный ledger, подтверждённые RUB-тарифы и правила окна суток. Без этих
зависимостей глобальный лимит не подключён; локальные ограничения одного запуска
его не заменяют. Точные интерфейсы — в [общей интеграции](../llm/INTEGRATION.md).

## Передача работ Backend1 и ML

После согласования зависимостей Backend1 регистрирует engine через существующий
`worker.tasks.set_ml_engine(runtime_engine)` в lifecycle приложения. Здесь эта
регистрация не выполняется. Действующий worker вызывает `generate_insight`;
для хранения companion-результата и технического отчёта потребуется отдельное
согласованное изменение worker/repository.

Публичные `MLInsightResult` и `EvidenceItem` остаются существующими DTO.
В старом `EvidenceItem` нет `source_id`, цитатного поля, document ID, страницы,
hash, классификации факта или ссылок на гипотезы. Внутренние структуры agent
эти данные передают. Публичную схему, хранение и миграции должны согласовать
Backend1 и ML; существующие API нельзя молча расширять только на стороне agent.
Frontend получает согласованную публичную проекцию и обязательный дисклеймер.

Предлагаемая текущая граница работ: ML поддерживает общий транспорт в llm,
промпты, структурированный анализ, проверки и run-local отчёты в agent; Backend1
поддерживает конфигурацию приложения, авторизацию, lifecycle, регистрацию,
публичные схемы, persistence и бюджет. Data/ETL предоставляет реальные наборы и
проверенные метаданные банковского корпуса. Историческое авторство каталога
`llm/` и прежние договорённости команды этим документом не устанавливаются.

Известные внешние проблемы backend остаются отдельными задачами: демонстрационный
seed с FK на отсутствующее событие, неполные totals после top-N, платежные
направления с бизнес-ярлыками, ограниченное ранжирование ленты и фиктивный учёт
бюджета. Работа над agent их не исправляет; владельцы назначаются командой.

## Автономная оценка

```powershell
& .\backend\app\agent\.venv\Scripts\python.exe -B -m backend.app.agent.evaluation
```

Команда не читает источники, `.env` или настройки процесса, не обращается к БД и
не вызывает настоящий LLM. Шесть вручную заданных синтетических сценариев
покрывают ставку, логистику, оборудование, валюту, регулирование и нерелевантное
событие. Явно разрешённый `FakeLLMClient` возвращает заранее написанный
`DraftInsight`, который проходит настоящий grounded verifier и projector.
Это проверка исполнения и структурных ограничений, а не интеллекта модели.

`evaluate_analysis(result)` считает технические показатели уже готового
`AgentAnalysisResult`, отдельно сравнивает fixture labels и возвращает перечень
обязательной экспертной оценки. Он не восстанавливает исходные тексты из URL и
не подтверждает смысл цитаты по одним метаданным. Общей оценки качества или
процента «точности LLM» нет. CLI печатает только режим, версию, безопасные
счётчики и ограничения проверки; содержимое инсайта и промптов не выводится.
