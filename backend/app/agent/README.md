# AI-компонент «Альфа-Будущее»

Одна поддерживаемая реализация: `AgentInsightEngine`. Python выбирает ограниченный
план, получает контекст через инструменты, LLM интерпретирует его, Python проверяет
ответ и формирует прежний `MLInsightResult`. Обычно нужен один LLM-вызов; разрешено
один дополнительный вызов: адресное исправление, исправление синтаксиса JSON или
повторная интерпретация после запроса недостающего контекста. Всего не более двух
банковских поисков, включая альтернативный запрос после пустого результата.
Это явный агентный процесс с накоплением наблюдений и общим пределом шагов.

**Автономно проверен компонент, а не полное приложение.** В текущем worker остаётся
`MockMLInsightEngine`, API вопросов возвращает заготовку. Новая реализация с настоящей
LLM ещё не проверена. Старые live B01/B03 относятся к предыдущей архитектуре.

```text
Компания + новость + переданная выборка платежей
  → Python-план по темам события и доступным инструментам
  → признаки компании / агрегаты платежей / банковский поиск / явные расчёты
  → накопленный контекст и неизменяемый для LLM каталог evidence
  → один структурированный ответ LLM
  → запрос контекста / verification → один ограниченный дополнительный шаг
  → повторная проверка → MLInsightResult + подробный companion-результат
```

## Файлы

| Файл | Ответственность |
|---|---|
| `orchestrator.py` | План, инструменты, deadlines, одно исправление или перепланирование, публичные методы |
| `planning.py` | Прозрачный Python-план и эвристическая сортировка кандидатов новостей |

| `demo.py`, `tests/` | Явный синтетический пример и автономные проверки |

## Какие данные используются

Из профиля берутся только предоставленные признаки: ОКВЭД, отрасль, география,
групповые и продуктовые флаги, форма организации/собственности, класс клиента,
категории возраста и работников ФНС/СПАРК. Диапазоны двух источников сохраняются
раздельно и не превращаются в точную численность. Выручка-заглушка `1000`
не становится известной выручкой. Год и валюта не угадываются. Продуктовый флаг
не доказывает получение кредита, остаток долга, ставку, график или условия договора.
`False` не доказывает отсутствие обязательств.

Платежи агрегируются по направлению и идентификатору контрагента. Поддержаны обе
реальные нотации backend: `PAYER/BENEFICIARY` и `CUSTOMER/SUPPLIER`. Самопереводы
учитываются отдельно и исключаются из концентрации внешних расчётов. Модели
передаются итоги и до трёх крупнейших участников каждого направления, а не все
строки. Конфликтующие имена не выбираются произвольно. Доли относятся исключительно
к переданной выборке. Платёж не устанавливает роль поставщика/покупателя, выручку,
валюту, период или всю сеть связей компании.

Банковский инструмент предоставляет ограниченные выдержки с датой, URL при
наличии, document/page/hash и статусом происхождения. Будущие относительно новости
источники отбрасываются. Разные даты публикации сохраняются: прогнозы разных
периодов не сливаются в один текущий факт и не объявляются автоматически
противоречием. Пустой поиск и ошибка источника различаются в отчёте.
Если ответ использует несколько банковских оснований, модель обязана явно
пометить необходимость сопоставления периодов, предпосылок или возможного
расхождения. Статус остаётся `unresolved`: разные даты сами по себе не доказывают
ни противоречие, ни согласованность. Это видно в `source_comparisons` и `ai_view`.

Дата события применяется до выбора top-N банковских материалов. Внутри уже
полученного длинного документа выбирается релевантный дословный блок с соседними
предложениями, а не всегда начало. Если тезис с соседними оговорками не помещается,
он исключается. Частичная выдержка отмечается в prompt, companion и ответах;
полноту всего исходного документа это не гарантирует.

Модель может запросить один дополнительный банковский поиск, если остались
лимиты источников, поиска и второго LLM-вызова. Новый контекст добавляется к
прежнему; исходные цитаты не заменяются. Изменение текста или метаданных того же
источника во время запуска вызывает отказ. Дополнительная интерпретация занимает
тот же единственный слот, что и исправление; третьего LLM-вызова не будет.

`BackendAnalyticsSource` — сохранённый ограниченный лексический адаптер, максимум
50 последних записей, а не поиск по всему корпусу. Настоящие embeddings, ACL,
PDF ingestion и RAG принадлежат backend. Сырой OCR не становится цитатой банка.

## Что проверяет grounding

LLM выбирает только существующие `evidence_ids`. Она не создаёт новые факты,
цитаты, ссылки, числовые метаданные или самостоятельные расчёты. Цитаты и цифры
в пользовательском результате подставляет Python из реально видимого каталога.
Условные механизмы должны ссылаться на событие и признаки данной компании.
Каналы планировщика задают приоритеты, а не закрытый список последствий.
Косвенный канал допустим, если условие/механизм связывает реальную тему события
с названным итоговым эффектом, например ставку с ипотечным финансированием и
спросом. Слова об итоговом эффекте не обязаны находиться в самой новости.
Это тематическая проверка объяснения; истинность причинной связи она не доказывает.

Проверяются неизвестные evidence/impact IDs, условность, известные конструкции
выдуманного полученного кредита и условий договоров, ложная уверенность,
произвольные числа и опасные рекомендации. Сохранение ключевой ставки не
обосновывает автоматическое изменение платежей по действующему договору.
Ошибки содержат код, путь поля и конкретный фрагмент для одной коррекции.
Аналитические названия допускают глаголы и существительные: «Проверить» /
«Проверка», «Сверка», «Запрос». Это не освобождает содержание от проверки:
исполнительные действия, неподтверждённые обязательства, числа и атрибуция банка
по-прежнему отклоняются.

Recovery передаёт нарушения с путями/фрагментами и предыдущий JSON один раз.
Факты сохраняются целиком, общие source metadata группируются по `source_id`;
дубли профиля и журнал исполнения повторно не отправляются. Проверяется размер
реально отправляемого контекста и всего prompt. Если обязательные данные всё же
не помещаются, запрос не выполняется: цитаты не обрезаются и лимиты не повышаются.

Только материал с доверенным `provenance_status="verified"` и документным
идентификатором может попасть в `bank_view`. `is_bank_analytics=True` недостаточно.
Неподтверждённые и синтетические материалы явно отделяются от позиции банка.
Статус `verified` должен устанавливать доверенный адаптер, а не пользовательский ввод.

**Verification не доказывает истинность экономического механизма.** Это конечные
структурные и лексические правила. Возможны пропуски сложных перефразировок и
ложные отклонения. Семантическая корректность, полезность и устойчивость к prompt
injection требуют отдельной экспертной проверки с настоящей моделью. Числовые
цитаты источников воспроизводятся с датами; самостоятельного извлечения и
семантического сопоставления всех чисел банковских прогнозов здесь нет.

## Неполные данные, действия и вопросы

Одна известная отрасль допускает полезные условные гипотезы о новом финансировании
или CAPEX. Недостаток входов для количественного эффекта не требует `insufficient`
для всего анализа. Нерелевантное событие может дать `insufficient` без искусственных
рисков. Это инструкция модели и проверяемый контракт; качество её выбора ещё
нужно измерить в live-тестах.

`ManagementActionEngine` работает по уже проверенному companion-результату без
дополнительных LLM-вызовов: отвечает по имеющимся источникам, возвращает связанные
условные механизмы, уточняющие данные и действия. Вопрос о неизвестной сумме долга
возвращает `needs_data`, даже при кредитном флаге. Это ограниченный grounded Q&A,
а не свободный чат или новый поиск. Проверяются компания, событие, evidence и
неизменность детерминированного результата. Авторизацию пользователя обеспечивает API.

Q&A может восстановить не выбранное для главного инсайта известное поле профиля
после сверки с текущей компанией и объяснить сохранённый перепроверенный расчёт
с параметрами, формулой, периодом и provenance. Это не подтверждение реального
долга по продуктовому флагу. Ответы по банковским материалам сохраняют даты
публикации, документ/page/hash и признак частичной выдержки.
Сохранённые качественные сценарии и требуемые данные выдаются отдельными
проекциями. Платёжный вопрос использует только сохранённые агрегаты, с явным
направлением и ограничением выборки; неизвестные роли и отсутствующие записи
не восстанавливаются. `review_plan` сохраняет названия, происхождение, режим
переданных пунктов и связь предложений с механизмами и evidence.

Сценарии ставки качественные, пока не передан `LoanSensitivityInput` с валютой,
договорной разницей ставки, периодом, типом ставки, reset и provenance. Python
считает `principal × delta_contract_rate × days / day_count_basis` через `Decimal`;
из движения ключевой ставки договорная разница не выводится. Для фиксированной
ставки ненулевой эффект без модели пересмотра отклоняется. CAPEX сопоставляется с
переданными фактическими денежными средствами, без вывода о платёжеспособности.
`actual` — заявление вызывающего кода, а не независимая проверка документов.

## Запуск без сети

Из корня репозитория, с уже установленными зависимостями:

```powershell
$py = '.\backend\app\agent\.venv\Scripts\python.exe'
& $py -B -m backend.app.agent.demo
& $py -B -m unittest discover -s backend/app/agent/tests -p 'test_*.py'
& $py -B -m unittest discover -s backend/app/llm/tests -p 'test_*.py'
& $py -B -m local_test_data.scenarios.run_agent_tests offline
```

Demo помечен `OFFLINE_FIXTURE_NOT_REAL_LLM`: синтетические данные и заранее заданный
JSON демонстрируют настоящий production-путь подготовки, проверки и проекции,
но не способность модели рассуждать. Runner использует 61 локальный сценарий;
данные и результаты остаются Gitignored. Инструкции live с отдельным согласием —
в `local_test_data/scenarios/RUNNER_README.md`. Автоматического live-запуска нет.

Импорт агента не читает `.env`, не создаёт соединение и не выбирает модель.
Нужен явно переданный клиент `async generate(prompt) -> str`. Production runtime
требует одобренные API model IDs и общий `BudgetedChatCompletionsClient`;
обычный HTTP-клиент без budget guard отклоняется до вызова. Настройка атомарного
командного хранилища, цен и корректной верхней оценки входных токенов принадлежит
backend/LLM; локальный предел вызовов этого не заменяет. Core допускает явно
переданный клиент для отдельно ограниченного локального стенда.

По умолчанию core: до двух LLM-вызовов, один дополнительный шаг, 30 секунд на вызов,
120 на анализ. Это не настройки DeepSeek live-стенда: там явно показываются
180/400 секунд и 8192 output tokens (опционально до 16384). Лимиты не повышаются
внутри агента. Ошибка синтаксиса JSON допускает одно исправление в том же общем
бюджете. Повторные ключи, NaN, неверная схема или превышение размера отклоняются;
ошибки транспорта не повторяются. Исчерпанные проверки завершаются диагностируемой
ошибкой, без фиктивного успешного инсайта.

## Что заменено

Удалены параллельный legacy engine, открытый tool/gather-цикл, старые цепочки
извлечения/разметки чисел и цитат, дублирующие smoke/harness-модули. В новом
контракте модель не генерирует эти факты: они принадлежат Python. Тесты старых
внутренних команд заменены проверками нового контракта; HTTP, публичная совместимость
и существенные отрицательные сценарии сохранены. Это не доказательство эквивалентности
всех эвристик двух архитектур.
