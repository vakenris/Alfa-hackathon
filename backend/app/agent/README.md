# AI-агент для анализа влияния новостей на компанию

Агент получает профиль компании, одну новость и выборку контрагентов. Он определяет,
какого доступного контекста не хватает, вызывает инструменты и формирует
структурированный бизнес-инсайт: событие, значимость, последствия, позицию банка,
вывод AI, рекомендуемое действие и evidence — ссылки на использованные источники.

Модуль автономен: для разработки и тестов не нужны API-ключ, БД или Redis.
По умолчанию используются `FakeLLMClient` и `MockAnalyticsSource`.
Реальная LLM, поиск/RAG и подключение к worker **пока не подтверждены и не интегрированы**.

## Архитектура

```text
Профиль + новость + контрагенты
  → ограниченный контекст
  → решение LLM: инструмент или готовый итог
  → результат инструмента добавляется в контекст → следующее решение
  → проверка MLInsightResult и происхождения evidence → итог
```

Цикл выполняет `AgentInsightEngine`, реализующий существующий
`MLInsightEngineProtocol` из `backend/app/ml/interface.py`.
Вход: `CompanyResponse`, `NewsArticleResponse`, `list[CounterpartyItem]` и tracer.
Выход: существующий `MLInsightResult`; публичные схемы бэкенда не меняются.
Вызовы модели идут через `LLMClientProtocol.generate(prompt: str) -> str`.
Нативный function calling провайдера не требуется: действия передаются текстовым JSON.
Состояние хранится только в пределах одного запуска.

## Что работает и что остаётся моками

| Часть | Текущее состояние |
| --- | --- |
| Многошаговый цикл | Реализованы выбор инструментов, раннее завершение, отдельная финализация, бюджеты и таймауты |
| Работа с данными | Реализованы ограничение контекста, сводка контрагентов, проверка JSON и происхождения evidence |
| Trace | Действия записываются через переданный tracer; `RecordingTracer` хранит их в памяти |
| LLM в автономных сценариях | `FakeLLMClient` выдаёт заранее заданные ответы; он не анализирует новости и не принимает решения самостоятельно |
| Банковская аналитика | `MockAnalyticsSource` возвращает переданные фикстуры; по умолчанию список пуст |
| HTTP-адаптер LLM | Реализован и проверен через `httpx.MockTransport`; работоспособность настоящего API не подтверждена |
| Worker | Совместимый контракт есть, но агент не зарегистрирован; бэкенд по-прежнему использует `MockMLInsightEngine` |
| Реальные материалы и RAG | Адаптера БД, реального поиска, загрузки материалов и RAG в модуле нет |

## Два инструмента

### `get_bank_analytics`

Получает банковские материалы через внедряемый `analytics_source=`.
Аргументы: `query` — строка до 256 символов, по умолчанию пустая;
`limit` — целое от 1 до 5, по умолчанию 3.

```python
async def search(
    query: str, *, company: CompanyResponse,
    event: NewsArticleResponse, limit: int,
) -> list[AnalyticsDocument]:
    ...
```

`AnalyticsDocument` содержит существующий `NewsArticleResponse` в поле
`article` и необязательный HTTP(S) `source_url`, полученный от источника данных.
Материалы без `is_bank_analytics=true` отклоняются.
Пустая успешная выдача допустима и отличается от ошибки инструмента.

Мок возвращает первые фикстуры, не ищет по запросу и не проверяет релевантность.
Позже адаптер БД, поиска или RAG сможет реализовать этот интерфейс без изменения
оркестратора. Он должен возвращать материалы с достоверными метаданными происхождения.

### `summarize_counterparties`

Не принимает аргументов. Группирует видимую выборку контрагентов по `direction`
и вычисляет число записей, сумму платежей и число транзакций по каждому направлению.
Это обычное вычисление на Python, без LLM и внешних запросов.

Суммы относятся только к переданной выборке. Период платежей и полнота сети
неизвестны; доли во всех платежах компании не вычисляются.
Пустая выборка не доказывает отсутствие связей у компании.

## Пример: один инструмент и итог без сети

Условная новость сообщает о повышении ставки, а в профиле завода отмечены кредитные
продукты. Сценарий ниже задаёт ответы fake-клиента: сначала запрос аналитики, затем
итог с оговоркой, что условия кредитов неизвестны. Мок аналитики возвращает пустой
список, поэтому позиция банка не предоставляется.

Выполните пример из корня репозитория в Python >= 3.12 с зависимостями проекта:

```python
import asyncio
import json
from datetime import datetime, timezone

from backend.app.agent import (
    AgentConfig, AgentInsightEngine, FakeLLMClient,
    MockAnalyticsSource, RecordingTracer,
)
from backend.app.schemas.company import CompanyResponse
from backend.app.schemas.event import NewsArticleResponse


async def main():
    company = CompanyResponse(
        id=1, synthetic_u="DEMO", name="Условный завод",
        cl_product_loa_mark=True,
    )
    event = NewsArticleResponse(
        id=10, title="Условная новость: ставка повышена",
        source="Демонстрационный источник", category="Экономика",
        published_at=datetime(2026, 10, 21, tzinfo=timezone.utc),
        content="Тестовый материал о повышении ставки.",
    )
    tool_call = {
        "action": "tool", "tool": "get_bank_analytics",
        "arguments": {"query": "ставка", "limit": 1},
    }
    final_result = {
        "what_happened": "В условной новости сообщается о повышении ставки.",
        "why_important": "В профиле завода отмечены кредитные продукты.",
        "consequences": "Влияние на расходы без условий договоров неизвестно.",
        "bank_view": "Позиция Альфа-Банка не предоставлена.",
        "ai_view": "Чувствительность расходов требует отдельной проверки.",
        "recommended_action": "Уточнить условия кредитных договоров.",
        "relevant_bank_product": None,
        "evidences": [{
            "claim": "В профиле отмечены кредитные продукты.",
            "source_title": "Профиль компании",
            "company_feature": "cl_product_loa_mark=true",
        }],
    }
    client = FakeLLMClient(responses=[
        json.dumps(tool_call, ensure_ascii=False),
        json.dumps(final_result, ensure_ascii=False),
    ])
    engine = AgentInsightEngine(
        client, analytics_source=MockAnalyticsSource(),
        config=AgentConfig(max_llm_calls=2),
    )
    tracer = RecordingTracer()
    result = await engine.generate_insight(company, event, [], tracer)
    print(result.model_dump_json(indent=2))
    print([step["step_name"] for step in tracer.steps])


asyncio.run(main())
```

Первый вызов возвращает действие инструмента, второй использует отдельный промпт
финализации и возвращает `MLInsightResult`. Результат и шаги остаются в памяти.

Для одного фиксированного ответа доступен `FakeLLMClient(response_json='...')`;
`AgentInsightEngine()` без аргументов возвращает явно демонстрационный ответ.
В `responses` можно передавать строки и исключения. При исчерпании сценария
возникает ошибка: последний ответ автоматически не повторяется.
Отправленные промпты доступны в `client.prompts`.

## Автономные тесты

Из корня репозитория, с Python >= 3.12, Pydantic v2 и HTTPX:

```powershell
python -B -W error -m unittest discover -s backend/app/agent/tests -v
```

Если зависимости установлены в локальное окружение агента:

```powershell
& .\backend\app\agent\.venv\Scripts\python.exe -B -W error -m unittest discover -s backend/app/agent/tests -v
```

Тесты используют fake-клиент, моки источника и `httpx.MockTransport`.
Они не требуют API-ключа, БД или Redis и не вызывают настоящий LLM API.
Проверяются многошаговый сценарий, инструменты, лимиты, таймауты, некорректный JSON,
evidence, изоляция запусков, сериализация HTTP-запросов и smoke check.
`-B` отключает создание bytecode, `-W error` превращает предупреждения в ошибки.

Если pytest установлен, альтернативная команда:

```powershell
python -B -m pytest backend/app/agent/tests -p no:cacheprovider
```

Обычный `pytest` без пути использует `backend/tests` из
`pyproject.toml`; его фикстуры создают БД. Это другой набор тестов.
Автономные тесты не подтверждают интеграцию с worker или работоспособность сервера LLM.

## Формат действий

На шаге планирования принимается одно действие:

```json
{
  "action": "tool",
  "tool": "get_bank_analytics",
  "arguments": {"query": "ставка", "limit": 3},
  "purpose": "Получить банковский контекст"
}
```

Для завершения — объект с `action="final"` и полем `result` по схеме
`MLInsightResult`. Для совместимости на шаге планирования также принимается
непосредственно `MLInsightResult`.
Неизвестный инструмент или некорректный управляющий JSON завершает запуск;
невалидные аргументы известного инструмента возвращаются как наблюдение об ошибке.

Наблюдение содержит `tool`, `arguments`, `status`, `data`, `error`.
Исходные данные и результаты инструментов считаются материалом для анализа;
промпт запрещает выполнять инструкции из их текста.

## Лимиты и финализация

`AgentConfig` передаётся через `config=`; счётчики локальны каждому запуску.

| Параметр | По умолчанию |
| --- | --- |
| `max_steps` / `max_llm_calls` | 4 / 4, включая итог |
| `max_tool_calls` | 3, включая ошибочные и повторные запросы |
| `tool_timeout_seconds` / `llm_timeout_seconds` / `run_timeout_seconds` | 5 / 30 / 120 секунд |
| `max_context_chars` | 24 000 символов накопленного JSON |
| `max_tool_result_chars` / `max_response_chars` | 8 000 / 24 000 символов |
| `max_article_chars` | 4 000 символов на content и summary до отметки сокращения |
| `max_counterparties` | 50 |

Число вызовов модели не превышает `min(max_steps, max_llm_calls)`.
Один шаг — одно решение модели; сообщений tracer может быть больше.
Последний разрешённый вызов использует отдельный промпт финализации и принимает
**только непосредственный `MLInsightResult`, без обёртки action/result**.
Ранний переход к финализации происходит при исчерпании бюджета инструментов,
повторе запроса или переполнении контекста. Невалидный итог завершает запуск
ошибкой без дополнительных вызовов и подставного успешного результата.

Контекст всегда остаётся валидным JSON: сокращаются тексты статей и выборка
контрагентов, а не сериализованная строка. Ограничения отмечаются в контексте;
не заданные поля исключаются, явно переданные `None` остаются `null`.
Часть бюджета резервируется под наблюдения. Если несокращаемые метаданные
не помещаются, запуск завершается до обращения к модели.

Результат инструмента сверх собственного или общего лимита целиком заменяется
`CONTEXT_LIMIT`. Старые результаты сохраняются, источники отклонённого результата
не становятся доступными для цитирования. Три длинных материала могут превысить
8 000 символов даже после сокращения: размер выдачи и бюджеты нужно согласовать
при подключении настоящего источника.

Бюджет контекста считается в символах JSON, не в токенах; постоянные инструкции и
схемы добавляются отдельно. `max_response_chars` проверяется после получения текста.
Лимит генерации API задаётся отдельно через `max_output_tokens`.

## Конфигурация HTTP-адаптера LLM

`ChatCompletionsClient` поддерживает один нестриминговый Chat Completions-совместимый
формат: `model`, `messages` и поле лимита в запросе;
`choices[0].message.content` и `finish_reason` в ответе.
Ожидается `finish_reason="stop"`. Значение `length` означает усечение;
другие причины завершения, отказ модели и отсутствие текста считаются ошибками.
Markdown и некорректный JSON автоматически не исправляются.

`ChatCompletionsConfig.from_env()` читает **только окружение процесса**:

| Переменная | Назначение |
| --- | --- |
| `AGENT_LLM_API_URL` | Обязательный полный URL запроса; путь не дописывается |
| `AGENT_LLM_MODEL` | Обязательный точный идентификатор модели |
| `AGENT_LLM_AUTH_HEADER` | Имя заголовка авторизации, если он нужен |
| `AGENT_LLM_AUTH_VALUE` | Полное значение заголовка, включая необходимый префикс |
| `AGENT_LLM_TIMEOUT_SECONDS` | Положительный timeout; по умолчанию 30 секунд |
| `AGENT_LLM_MAX_OUTPUT_TOKENS` | Положительный лимит генерации; по умолчанию 1024 |
| `AGENT_LLM_TOKEN_LIMIT_FIELD` | `max_tokens` по умолчанию либо `max_completion_tokens` |

Endpoint, модель, авторизацию и поддерживаемое поле лимита нужно подтвердить
у команды API. `Bearer` автоматически не добавляется. Заголовок и значение
задаются вместе; если оба отсутствуют, запрос отправляется без авторизации.
Клиент сам не проверяет разрешённый список моделей кейса.

Файлы `.env` не загружаются; настройки `LLM_*` из бэкенда не используются.
Наличие параметров в окружении само по себе не включает реальную LLM:
`ChatCompletionsClient` нужно явно передать движку вместо fake-клиента.
Такой клиент без `MockTransport` при вызове `generate()` отправляет настоящий запрос.
До отдельного согласования используйте fake-клиент и HTTP-моки.

Секрет скрыт в представлении конфигурации. Не сохраняйте ключи в коде,
документации или Git. В тестах используются только заведомо тестовые значения.

## Ошибки, trace и usage

На уровне агента доступны безопасные исключения:

| Исключение | Причина |
| --- | --- |
| `AgentResponseError` | Невалидный JSON, действие или итог; превышение размера ответа |
| `AgentEvidenceError` | Неполученный/неоднозначный источник, неверный URL или признак компании; отсутствие evidence для позиции банка |
| `AgentContextError` | Невозможно сформировать контекст в пределах бюджета |
| `AgentLLMError` | Сбой клиента модели; включает ошибки HTTP-адаптера |
| `AgentLLMTimeoutError` | Собственный deadline LLM-вызова в оркестраторе; наследует `AgentLLMError` |
| `AgentTimeoutError` | Превышен общий deadline запуска |

В наблюдениях инструментов используются коды `INVALID_ARGUMENTS`, `TOOL_TIMEOUT`,
`TOOL_FAILED`, `INVALID_TOOL_RESULT`, `DUPLICATE_REQUEST`, `CONTEXT_LIMIT`.
Одинаковые запросы, включая явно заданные значения по умолчанию, не выполняются
дважды. Повтор переключает следующий вызов на финализацию.
Автоматических повторов и fallback на другой источник/LLM нет.

HTTP-адаптер отдельно различает `LLMTimeoutError`, `LLMTransportError`,
`LLMHTTPError` с `status_code`, `LLMResponseError`, `LLMOutputLimitError`.
Все наследуют `LLMAPIError`; движок оборачивает ошибки клиента в `AgentLLMError`.
Невалидная конфигурация вызывает Pydantic `ValidationError` до запроса.
На один `generate()` приходится одна HTTP-попытка; redirects отключены,
HTTP-клиент закрывается после запроса. Системные proxy не используются
(`trust_env=False`). Действуют HTTP-timeout и общий deadline запроса.

Через `tracer.emit_step()` записываются действия, счётчики, ограничения и коды
ошибок, без полных промптов, приватных ответов и внутренних рассуждений модели.
Отмена задачи и ошибки tracer не скрываются. Исключения агента могут обрабатываться
существующим FAILED-путём worker, но это подключение ещё не выполнено.

`client.last_usage` хранит исходный объект usage последнего вызова, отдельно от
`MLInsightResult`. Отсутствующий/null usage — `None`, пустой объект остаётся `{}`;
счётчики не вычисляются. Usage сохраняется при усечении ответа и последующей
ошибке валидации. В начале следующего вызова он сбрасывается; после сетевого сбоя
затраты неизвестны, а не равны нулю. Для параллельных jobs нужны отдельные клиенты.
Это не суммарный учёт нескольких шагов и не контроль дневного бюджета команды.

## Проверка происхождения evidence

Каталог источников строится только из исходного профиля, видимой выборки
контрагентов, исходной новости и принятых результатов инструментов.

- `source_title` должен однозначно определять полученный источник.
- Ненулевой `source_url` должен точно совпадать с URL именно этого источника.
  URL внутри текста статьи или ссылка другого материала не подходят.
- Синтетические названия источников: `Профиль компании` и `Контрагенты компании`.
- `company_feature` — `null` или точная пара `поле=JSON_значение`
  из показанного профиля, например `cl_product_loa_mark=true`.

Без банковских материалов поле `bank_view` принудительно устанавливается в
`Позиция Альфа-Банка не предоставлена.`; замена текста отмечается в trace.
При наличии материалов для другого значения требуется хотя бы один evidence
на банковский источник. Без каталога продуктов `relevant_bank_product`
устанавливается в `null`, также с записью в trace.

Это **не фактчекинг**: проверяется происхождение источника, а не следование
утверждения из его текста. В публичном evidence нет source_id, цитаты и
структурированной связи с bank_view. Поэтому неоднозначные названия отклоняются,
но наличие банковской ссылки не доказывает правильность пересказа позиции банка.
Атрибуция в остальных свободных текстовых полях ограничивается промптом;
надёжной семантической проверки нет. Метка `is_bank_analytics` должна поступать
от доверенного источника данных и сама не подтверждает подлинность публикации.

В существующей схеме новости бэкенда нет URL; для таких материалов URL остаётся
`null`. Внутренняя обёртка `AnalyticsDocument` позволяет будущему адаптеру
передавать URL без изменения публичного контракта.

## Smoke check API организаторов

`smoke_check.py` содержит ранее переданные адрес и модель:
`https://changellenge.up.railway.app/v1/chat/completions` и
`deepseek/deepseek-v4.1-flash`. Доступность endpoint, модели и схема авторизации
**ещё не подтверждены сервером**.

Профиль фиксирован: `Reply only OK.`, 32 выходных токена, timeout 30 секунд,
одна попытка. Это проверка транспорта, а не полного анализа новости.

Без флага выполняется только HTTP-мок:

```powershell
& .\backend\app\agent\.venv\Scripts\python.exe -B -m backend.app.agent.smoke_check
```

Вывод содержит безопасный план запроса и usage, если он предоставлен.
Авторизация скрыта; текст модели и тела ошибок не печатаются.
`usage=null` означает отсутствие статистики. Успешный мок не доказывает
работоспособность сервера.

Режим `--send` отправляет **один настоящий запрос** и требует отдельного разрешения.
Без настроенной авторизации он блокируется до вызова клиента.
Полное значение заголовка можно задать без показа и записи секрета в историю:

```powershell
$env:AGENT_LLM_AUTH_HEADER = Read-Host 'Имя заголовка по инструкции команды'
$smokeHeaderValue = Read-Host 'Полное значение заголовка' -AsSecureString
$env:AGENT_LLM_AUTH_VALUE = [System.Net.NetworkCredential]::new('', $smokeHeaderValue).Password
```

При необходимости команда может задать
`AGENT_LLM_TOKEN_LIMIT_FIELD=max_completion_tokens`.
URL, модель, timeout и небольшой лимит smoke-профиля фиксированы в модуле;
остальные переменные не переопределяют их. При усечении ответа повторов и
автоматического увеличения лимита нет; усечение само по себе не доказывает
несовместимость API.

## Smoke check полного движка

`engine_smoke_check.py` проверяет существующий `AgentInsightEngine` целиком:
выбор `get_bank_analytics`, выполнение `MockAnalyticsSource`, передачу результата
во второй промпт, принудительную финализацию и валидацию `MLInsightResult`/evidence.
Компания, новость, два контрагента и банковский материал полностью синтетические.
Это проверка без worker, БД и настоящего поиска/RAG.

По умолчанию оба ответа формирует HTTP-мок, но сериализацию запросов и разбор
ответов выполняет настоящий `ChatCompletionsClient`:

```powershell
& .\backend\app\agent\.venv\Scripts\python.exe -B -m backend.app.agent.engine_smoke_check
```

Первый промпт просит выбрать инструмент, не подставляя ответ модели. Уникальный
тестовый тезис появляется только в документе, возвращённом инструментом. Успех
требует его дословного включения в `bank_view` и точного совпадения цитаты,
названия и URL документа в evidence. Одной ссылки без использования тезиса
недостаточно. Это контролируемая проверка передачи и использования данных,
а не семантический фактчекинг. Ранний итог или другой инструмент не засчитываются
как успешная проверка полного цикла.

Компактные инструкции включаются **только в финализации smoke-теста**:
одно короткое предложение на текстовое поле, ориентир до 120 символов,
один JSON-объект без отступов и ровно один evidence на выданный документ.
Обязательная цитата всегда сохраняется целиком и повторяется только в
`bank_view` и `evidence.claim`. Все поля `MLInsightResult` остаются на месте;
`relevant_bank_product` и `company_feature` в этом сценарии равны null.
Это инструкция модели, а не обрезка результата или ограничение публичной схемы.
Обычные промпты `AgentInsightEngine` не включают этот режим, подробные инсайты
и несколько evidence по-прежнему допускаются.

Вызовы ограничены на двух уровнях: `AgentConfig` разрешает два шага/LLM-вызова
и один запрос инструмента, а обёртка клиента блокирует третью HTTP-попытку.
Ошибочные попытки также расходуют лимит. Второй вызов использует отдельный
промпт финализации. Повторов, автоматического увеличения лимитов и fallback нет.
По умолчанию лимит составляет 1536 выходных токенов на каждый запрос.
Параметр CLI `--max-output-tokens` явно задаёт целое число от 1 до 8192;
границы одинаковы для HTTP-мока и live-режима. Выбранное значение применяется
к обоим LLM-вызовам, включая финализацию, и отображается в
`max_output_tokens_per_call`. Некорректное значение отклоняется до обращения к API.
Тайм-ауты задаются независимо и отображаются в `timeouts_seconds`:

| Параметр CLI | По умолчанию | Максимум |
| --- | --- | --- |
| `--http-timeout-seconds` | 30 секунд | 120 секунд |
| `--llm-timeout-seconds` | 40 секунд | 130 секунд |
| `--run-timeout-seconds` | 90 секунд | 300 секунд |

Принимаются конечные положительные числа, включая дробные. Некорректные значения
отклоняются до создания клиента. Рекомендуемый порядок: HTTP < LLM < общий timeout.
Десятисекундный запас между HTTP и LLM по умолчанию позволяет HTTP-адаптеру
сообщить собственную ошибку до отмены оркестратором. Более короткие внешние
тайм-ауты также допустимы и получают отдельную диагностику. Эти настройки
применяются только к smoke-тесту; обычные значения `AgentConfig` не меняются.
Неизвестные входные затраты тайм-аутами не оцениваются.

Например, проверка повышенного лимита через HTTP-мок, без платных запросов:

```powershell
& .\backend\app\agent\.venv\Scripts\python.exe -B -m backend.app.agent.engine_smoke_check --max-output-tokens 4096
```

Настройки адреса, модели, заголовка/значения авторизации и поля лимита берутся
из `AGENT_LLM_API_URL`, `AGENT_LLM_MODEL`, `AGENT_LLM_AUTH_HEADER`,
`AGENT_LLM_AUTH_VALUE`, `AGENT_LLM_TOKEN_LIMIT_FIELD`. Если адрес и модель
не заданы, используются те же значения организаторов, что в обычном smoke check.
Ключ читается только из окружения процесса; `.env` не загружается.
`AGENT_LLM_MAX_OUTPUT_TOKENS` не задаёт лимит этого проверочного профиля:
для изменения используется только `--max-output-tokens`.
`AGENT_LLM_TIMEOUT_SECONDS` также не меняет тайм-ауты smoke-теста: для этого
используются перечисленные параметры CLI. Автоматического увеличения нет.

Только после отдельного разрешения пользователя можно выполнить:

```powershell
& .\backend\app\agent\.venv\Scripts\python.exe -B -m backend.app.agent.engine_smoke_check --send --max-output-tokens 4096 --http-timeout-seconds 120 --llm-timeout-seconds 130 --run-timeout-seconds 300
```

Без настроенного заголовка и значения авторизации реальная отправка блокируется.
Разрешение на реализацию модуля или запуск его HTTP-мока не разрешает платные запросы.
Первый live-тест дошёл до финализации, но завершился `LLMOutputLimitError`
на втором вызове. Успешный полный live-цикл после изменения промпта ещё не подтверждён.

Отчёт содержит только режим, счётчики, выбранный инструмент, результаты проверок,
безопасные коды ошибок и известные числовые поля usage для каждой попытки.
Заголовки, ключ, промпты, уникальный тезис, полный инсайт и тела ошибок не выводятся.
Usage сохраняется и при усечении ответа или ошибке JSON. Отсутствие usage не
ломает проверку результата и не вызывает повтор: `usage_complete=false`,
неизвестные суммы остаются `null`, а не превращаются в нулевой расход.
Для каждой попытки дополнительно выводятся безопасные поля:

- `elapsed_ms`: длительность попытки клиента по монотонным часам, включая
  HTTP-запрос и разбор ответа; сохраняется при ошибке и отмене. Одноимённое поле
  в корне отчёта измеряет весь сценарий, включая инструменты и валидацию.
- `timeout_kind`: `http_connect`, `http_read`, `http_write`, `http_pool`,
  `http_timeout` для ошибок HTTPX, `http_deadline` для общего deadline HTTP-запроса,
  `unknown_timeout` для `TimeoutError` без подтверждённого владельца,
  `llm_deadline` или `scenario_deadline`; null при отсутствии тайм-аута.
- `cancellation_kind`: `llm_deadline` / `scenario_deadline` для отменённой
  активной попытки либо `external_or_unknown`, если внутренние deadline не
  подтверждены. Завершённая попытка не помечается отменённой, если общий
  тайм-аут наступил позже, например во время выполнения инструмента.
- `finish_reason`: `stop`, `length`, `other` для неизвестной строковой причины
  либо null при отсутствии данных. Произвольный текст причины от провайдера не печатается.
- `content_chars`: число символов в `message.content` до обработки усечения.
  Ноль означает пустую строку, null — отсутствие строкового содержимого.
- `reasoning_tokens`: только неотрицательное целое из
  `usage.completion_tokens_details.reasoning_tokens`, если сервер его предоставил;
  иначе null. Содержимое рассуждений не читается для отчёта и не выводится.

Эти поля сбрасываются перед каждым запросом и сохраняются при `finish_reason=length`.
Даже полный JSON в усечённом ответе не принимается за успех. Reasoning-токены
показываются отдельно и не прибавляются повторно к `completion_tokens`/`total_tokens`.
`usage_complete` относится к трём основным счётчикам, а не к наличию детализации
рассуждений. Длина в символах не приравнивается к токенам; автоматических
оценок и увеличения лимита нет. Отчёт помогает различать гипотезы об усечении,
но компактный HTTP-мок не гарантирует такую же длину ответа настоящей модели.

HTTP-тайм-аут завершается кодом `LLMTimeoutError`, тайм-аут оркестратора —
`LLMCallTimeout`, общий — `ScenarioTimeout`; они больше не сводятся к общей
ошибке `LLMCallFailed` / `AgentFailed`. При отмене до ответа `usage` остаётся null:
это не доказывает, что провайдер прекратил генерацию или не списал токены.
Внешний `CancelledError` распространяется вызывающему коду, без повтора и
подставного итогового отчёта; метаданные уже начатой попытки сохраняются в
обёртке клиента. CLI при Ctrl+C печатает краткий `Interrupted` с `elapsed_ms`
и `cancellation_kind=keyboard_interrupt` и завершает работу с кодом 130.

Код завершения: 0 — полный сценарий пройден; 1 — ошибка/неполный сценарий;
2 — неверная конфигурация; 130 — прерывание пользователем.

## Что согласовать перед интеграцией

Регистрацию через `worker.tasks.set_ml_engine()`, источник настоящих материалов,
жизненный цикл сессий/клиентов, даты публикаций и политику кэша инсайтов.
Словарь `direction` требует согласования: комментарий схемы содержит
`PAYER/BENEFICIARY`, репозиторий возвращает `CUSTOMER/SUPPLIER`.
Также неизвестны полнота выборки и источник разрешённых банковских продуктов.

Эти задачи не закрываются автономными тестами. Полноценный RAG, сложная память
и дополнительные сервисы для текущего автономного прототипа не требуются.
