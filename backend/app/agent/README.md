# Агент персонализированной новостной аналитики

Основной `AgentInsightEngine.generate_insight()` выполняет ограниченный анализ
с источниками, структурированным черновиком, проверкой оснований и одной
recovery-веткой. Возвращается прежний `MLInsightResult`.
`generate_analysis()` дополнительно возвращает гипотезы, действия, provenance,
ограничения и отчёт вызовов.

**Это автономно проверенный модуль, требующий подключения к приложению.**
Worker в проверенном backend по-прежнему использует `MockMLInsightEngine`.
В автономных проверках не используются настоящие банковские PDF, БД или API;
сквозной frontend не проверен. Предыдущий live-тест пользователя не заменяет
проверку полного приложения.

## Основной путь

```text
Профиль + новость + выборка платежных связей
  → известные признаки и пробелы бизнес-контекста
  → выбор инструмента / адаптация поиска
  → DraftInsight: цитаты + условные механизмы влияния
  → проверки оснований, чисел, времени и ссылок
  → максимум одна ветка repair или search_then_redraft
  → повторная проверка → детерминированный MLInsightResult
```

Нужен явно переданный LLM-клиент. Конструктор не читает `.env` и не создаёт
сетевой клиент. Основной движок без явного клиента завершается ошибкой
конфигурации, без подмены анализа фиктивным результатом.

`RuntimeAgentEngine` получает `client_factory` и `source_factory`, создаёт
зависимости на каждый запуск и требует grounded-режим. Некорректные зависимости
и `None` отклоняются. Fake/Mock разрешаются только через явный
`allow_test_dependencies=True` для автономных проверок.
Для production `ChatCompletionsClient` требуется переданный backend список
`approved_model_ids`; aliases gateway нельзя угадывать.

## Проверки и их пределы

- Источник действительно включён в видимый контекст текущего запуска.
- Цитата точна и сохраняет границы высказывания: нельзя вырезать «не».
- Банковская цитата берётся из `content` с `provenance_status=verified` и
  `source_document_id`. Один `is_bank_analytics=true` этого не доказывает.
- Гипотезы не содержат выдуманных цифр, гарантий, приписанной банку позиции
  или утверждённых неизвестных договорных условий.
- Гипотеза связана с фактом события и известным признаком компании;
  проверяются минимальные тематические условия канала влияния.
- Числовые сопоставления требуют entity/metric/unit/period/value из цитаты.
  Одиночное число без scope может быть процитировано с предупреждением,
  но не превращается в рассчитанный эффект. Несколько таких числовых
  утверждений без scope нельзя синтезировать как непротиворечивые факты.
- Сопоставимые размеченные противоречия обозначаются и не становятся
  однозначной причинной предпосылкой.
- Источники позднее даты анализируемого сообщения отклоняются.
  Исторические материалы маркируются; их прогнозы не объявляются текущими.

**Программные проверки не доказывают истинность причинных связей.**
Лексическая применимость и точная цитата не заменяют семантический фактчекинг.
Выводы показываются как условные гипотезы AI, с допущениями и данными для
проверки. Сложные смысловые противоречия, полнота разметки модели и
правдоподобные, но неверные механизмы остаются предметом экспертной оценки.

### Качественный анализ при неполных данных

Неизвестные долг, договорные ставки и CAPEX блокируют расчёт финансового эффекта,
но не условную отраслевую гипотезу. Для производственного профиля решение о
ключевой ставке позволяет рассмотреть будущее финансирование и инвестиционные
решения, явно обозначив наличие таких планов как допущение. Из сохранения ставки
не следует изменение действующих платежей или равенство договорной ставки ключевой.

Узкий контроль полноты распознаёт самостоятельное утвердительное сообщение о
решении Банка России и производственный ОКВЭД 10–33. Преждевременный `insufficient`
даёт `QUALITATIVE_ANALYSIS_MISSING` и максимум одну recovery-ветку. Отрицания,
гипотетические решения и случайные упоминания не включают этот контроль.
Это не универсальный классификатор релевантности: другие формулировки и отрасли
оценивает модель. Нерелевантное событие по-прежнему допускает `insufficient`.

## Семантика данных

`revenue_company=1000` — неизвестная выручка, raw DTO не меняется.
Для набора кейса выручка относится к 2025 году и RUB. False/default/null
не доказывают отсутствие обязательств. Кредитный продукт не задаёт долг,
тип ставки или финансирование инвестиций.

Grounded-контекст переводит `SUPPLIER/BENEFICIARY` в `outgoing`,
`CUSTOMER/PAYER` в `incoming`, отдельно выделяет self transfers.
Это финансовые направления, а не доказанные хозяйственные отношения.
Суммы относятся к выборке; платежи не подменяют выручку или расходы.
FAQ указывает «с 1 января», без года и конечной даты.

Группа, отсутствующие профили контрагентов, импорт/экспорт и рыночная доля
не достраиваются. `negative_mark` — сведения о ключевом собственнике,
а не отрицательный риск. Страны ФТС не задают товар, объём или направление.

## Источники

Сохраняется `AnalyticsSourceProtocol.search(query, *, company, event, limit)`.
`BackendAnalyticsSource` принимает внедрённый загрузчик `AnalyticsDocument`.
`from_repository_factory()` использует существующий `NewsRepository`,
импортируя его и открывая сессию только при явном поиске.

Fallback ранжирует **не более 50 последних материалов** по словам и темам:
это не RAG и не поиск по полному корпусу. Пустая выдача отличается от ошибки.
Старые документы сохраняются. URL не загружаются и не придумываются.
По умолчанию repository provenance — `unverified`; доверенный внешний
resolver передаёт проверенные ID/страницу/URL/hash. Настоящий search/RAG
бэкендера №2 внедряется без дублирования загрузки PDF и индекса.

## Лимиты и отчёты

Обычный профиль: до четырёх LLM-вызовов, трёх tool calls и одной recovery-ветки.
Есть HTTP/LLM/run/trace deadlines; ошибки расходуют слоты. Часть бюджета
резервируется для черновика и исправления. Проекция результата не вызывает LLM.
Автоматического повышения лимитов и скрытых повторов нет.

Если нет платежей и фиксированный mock-корпус пуст, grounded-путь сразу запрашивает
черновик. Пользовательские и production-источники не объявляются пустыми заранее;
пустая выдача одного запроса не запрещает другой поиск. Недоступные инструменты
исключаются из описаний и prompt-схемы, а также отклоняются при исполнении.
Из JSON Schema убраны только служебные аннотации; runtime-валидация неизменна.
Repair передаёт прежний черновик без необязательных пустых/default/null полей,
сохраняя цитаты и заполненные числовые scope. Модель просят сохранять полезные
условные механизмы при исправлении нарушений.

Размер полного prompt проверяется со схемами и инструкциями.
HTTP-ответ читается с ограничением байтов; усечённый ответ не принимается.
Trace не содержит chain-of-thought, секретов, полных ответов или сырой ошибки.

`RunReport` разделяет полные известные `totals` и `known_subtotal`.
Отсутствующий usage — null, не ноль. Reasoning не прибавляется повторно.
Изменяемые `last_*` сбрасываются перед попыткой; read-only custom metadata
без обновляемого `last_attempt_id` считается неподтверждённой.
Отмена распространяется и несёт безопасный `run_report`.
Общего `last_report` или `last_analysis` нет.

`calls[].prompt_chars` показывает размер входного prompt.
`validation_attempts` сохраняет номер вызова, этап, коды нарушений и количество
фактов/гипотез, без содержимого черновика или рассуждений. Эти данные объясняют
переход к repair даже при успешной итоговой проверке. Сокращение размера prompt
не гарантирует сокращения скрытых reasoning-токенов конкретной модели:
для этого нужен отдельно разрешённый повторный live-тест.

Командные 500 ₽ и тарифы не заменяются локальным фиктивным счётчиком.
Backend должен связать отчёты с централизованным контролем расходов.

## Управленческие действия и вопросы

`ManagementActionEngine(core).analyze_action(request, *, analysis, company, tracer)`
использует доверенный `AgentAnalysisResult` этой же компании:

- `rate_scenario`: повышение, снижение или сохранение ставки;
- `investment_budget`: предложения по инвестиционным расходам;
- `review_plan`: предложения к предоставленному плану;
- `question`: выбор существующих фактов, гипотез и признаков по вопросу.

Сценарии детерминированы; предложения не выполняются и не сохраняют план.
Недостающие данные дают `needs_data`. Q&A ограничивает LLM выбором ссылок;
новый свободный текст модели не становится ответом или фактом.
Количественные договорные вопросы без исходных параметров требуют уточнения.

Чувствительность считается только по явным входам:
`principal * delta_contract_rate * days / day_count_basis` в Decimal.
Договорная разница ставки не выводится из изменения ключевой.
Результат сохраняет формулу, происхождение, предположения и
`is_financial_forecast=false`. Декларация пользователя actual
не является независимой проверкой финансовых документов.

Каждый результат содержит дисклеймер. Полные API и handoff —
в [INTEGRATION.md](INTEGRATION.md).

## Проверка без сети и БД

Из корня репозитория:

```powershell
& .\backend\app\agent\.venv\Scripts\python.exe -B -m unittest discover -s backend/app/agent/tests -p 'test_*.py'
& .\backend\app\agent\.venv\Scripts\python.exe -B -m backend.app.agent.evaluation
```

Evaluation использует заранее заданные synthetic drafts и проверяет технические
свойства пути. Он не измеряет интеллект или реальное качество LLM.
Нужны экспертная разметка и отдельно разрешённый live-тест.

Root pytest настроен на backend/tests. Общие backend fixtures могут менять
настроенную БД: не запускать их в автономной проверке агента.

## Совместимость

`CompatibilityInsightEngine` явно сохраняет прежний JSON-loop и provenance-only
проверку для старых fixtures и транспортного smoke. Это не строгий production
engine. Старые 127 проверок сохранены; импорты соответствующих тестов указывают
этот режим явно, assertions не ослаблены. Новый основной путь покрыт
grounded/adversarial тестами.

`engine_smoke_check` проверяет старый синтетический двухзапросный сценарий,
по умолчанию через HTTP-мок. Его успех не подтверждает новый grounded-путь
или настоящий банковский поиск. Реальные запросы не запускались;
для них нужно отдельное разрешение.

## Незакрытая интеграция

Единственная реализация HTTP-транспорта и его конфигурация теперь находятся в
`backend/app/llm/client.py`. Старые импорты из `agent/api_client.py` и
`agent/config.py` сохранены через re-export. Общий слой дополнен явным router,
необязательным кэшем проверенных результатов и бюджетным клиентом с обязательным
внешним атомарным ledger. Без такого хранилища, тарифов и правил суток защита
командного лимита не подключена. Публичные схемы коллег из `origin/Backend`
не дублируются. Передача работ описана в [общей интеграции](../llm/INTEGRATION.md).

Не подтверждены: настоящий LLM endpoint и aliases, качество на реальных PDF,
PostgreSQL/worker/SSE, общий бюджет и React → API → agent.
